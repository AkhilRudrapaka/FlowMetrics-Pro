# Deploy FlowMetrics Pro on Render (free tier)

About 20 minutes the first time, no credit card needed. You will create a free MongoDB database on **Atlas**, then one free **Render web service** that runs both the API and the web UI.

```
 Browser ──HTTPS──▶  https://flowmetrics-pro.onrender.com   (one Render Docker service)
                       ├─ serves the React UI   (/ , /assets/…)
                       └─ serves the Go API     (/api/v1/…)  ──TLS──▶  MongoDB Atlas (free)
```

## Why one service instead of a separate static site and API?

- **Login depends on one origin.** The session is a `SameSite=Strict` cookie. `onrender.com` is a public suffix, so `ui.onrender.com` and `api.onrender.com` count as *different sites*: the browser would never send the cookie and every page reload would log you out. Serving the UI from the API keeps one origin, so **no CORS and no API-URL setting are needed**: the UI calls the relative path `/api/v1`.
- **It fits the free tier.** One service uses about 744 of your 750 free instance hours a month.
- **Docker Compose is untouched.** Locally you still get nginx and a separate API container (`docker compose up`). Render uses the root `Dockerfile` instead, which builds the UI and the API into a single image.

## 0. Push the code to GitHub

Render deploys from GitHub, so everything in this repo (including `render.yaml` and the root `Dockerfile`) must be on `main`:

```bash
git status            # should be clean
git push origin main
```

## 1. Create the database (MongoDB Atlas, free)

Render has no managed MongoDB, so use Atlas. Button names move around a little; the idea stays the same.

1. Sign up at **https://cloud.mongodb.com** and create a project (the default is fine).
2. **Create a cluster**: choose the **Free** tier. Provider **AWS**, region **Oregon (us-west-2)** (it sits next to Render's default Oregon region, which keeps queries fast). Name it `flowmetrics`. Create.
3. **Create a database user** (Security → *Database Access* → *Add New Database User*):
   - Username `flowmetrics`, authentication *Password*.
   - Password: **letters and digits only** (a symbol such as `@` or `/` must be URL-encoded in the connection string, and forgetting is the #1 cause of auth errors).
   - Role: **Read and write to any database**.
4. **Allow Render to connect** (Security → *Network Access* → *Add IP Address*): choose **Allow access from anywhere** (`0.0.0.0/0`).
   *Why:* free Render services share outbound IP ranges and have no fixed address. The database is still protected by its long password and TLS. For a tighter setup, add Render's outbound ranges instead (Render dashboard → your service → *Connect* → *Outbound*).
5. **Get the connection string**: *Database → Clusters → Connect → Drivers → Go*. Copy the URI. It looks like:

   ```
   mongodb+srv://flowmetrics:<db_password>@flowmetrics.ab1cd.mongodb.net/?retryWrites=true&w=majority&appName=flowmetrics
   ```

   Replace `<db_password>` with your real password (remove the `<` `>`). Keep this string; you paste it into Render in step 2. **Treat it like a password.** Don't put it in the repo.

## 2. Create the web service (Render Blueprint)

1. Sign in at **https://dashboard.render.com** (use *Sign in with GitHub*).
2. **New + → Blueprint**. Connect your GitHub account if asked and grant access to the `FlowMetrics-Pro` repository. Select it, branch `main`.
3. Render reads `render.yaml` and shows one service, **flowmetrics-pro** (Docker, *Free*). It asks you for **`MONGO_URI`**: paste the Atlas string from step 1.
4. Click **Deploy Blueprint** (the button may read *Apply*). The first build takes about 3 to 6 minutes (it compiles the UI and the Go server). Open the service → **Logs** and wait for:

   ```
   seed: demo data created   users=4 orgs=2 projects=5 tasks=26
   serving web UI            dir=/public
   listening                 addr=:10000 env=production
   ```

   and the service status to turn **Live**. Its URL is at the top of the page: `https://flowmetrics-pro.onrender.com` (Render adds a suffix if the name is taken).

> **Prefer clicking through instead of a Blueprint?** *New + → Web Service → Build and deploy from a Git repository →* pick the repo → **Language: Docker**, **Instance type: Free**, **Region: Oregon**, **Health Check Path: `/healthz`**, then add the environment variables below by hand.

## Environment variables

`render.yaml` sets all of these for you; this is what each one does. You only ever type `MONGO_URI`.

| Variable | Value on Render | Why |
| --- | --- | --- |
| `MONGO_URI` | your Atlas `mongodb+srv://…` string | **You provide this.** Marked `sync: false`, so it is never stored in the repo |
| `JWT_SECRET` | *generated by Render* (random 256-bit) | Signs login tokens. The server refuses to start with a weak or placeholder secret |
| `APP_ENV` | `production` | JSON logs; rejects placeholder secrets |
| `COOKIE_SECURE` | `true` | The refresh cookie is only sent over HTTPS (Render serves HTTPS) |
| `MONGO_DB` | `flowmetrics` | Database name inside the Atlas cluster |
| `BCRYPT_COST` | `10` | The free instance has a fraction of a CPU; 10 keeps login quick (still OWASP-acceptable) |
| `CLIENT_IP_HEADER` | `CF-Connecting-IP` | Render is behind Cloudflare; this makes the login rate limiter see each real visitor instead of one shared proxy address |
| `TRUSTED_PROXIES` | private ranges | Fallback if that header is absent |
| `SEED_ON_START` | `true` | Creates the demo accounts on the first start (skipped when they already exist) |
| `PORT`, `STATIC_DIR` | *(automatic)* | Render injects `PORT=10000`; `STATIC_DIR=/public` is baked into the image |

Not used on purpose: `CORS_ALLOWED_ORIGINS` (single origin) and any "API URL" for the frontend (it calls `/api/v1` on its own origin).

## 3. Verify (checklist)

Open your Render URL. The first request after a sleep can take about a minute; Render shows a "waking up" page.

- [ ] `https://<your-service>.onrender.com/healthz` shows `{"status":"ok"}`
- [ ] The home page loads and redirects to the login page (with a "Demo data is loaded" box)
- [ ] Sign in as `alice@acme.test` / `Password123!`: you see the organization picker (Acme Corp and Globex Inc)
- [ ] Open *Acme Corp → Website Redesign* and **drag a card** to another column; **refresh the page**: the card stays, and you are *still signed in* (this proves the cookie works)
- [ ] Sign out, then sign in as `dave@globex.test`: he sees only Globex; pasting an Acme URL shows "Not found"
- [ ] Register a brand-new account: you land on an empty workspace and can create an organization
- [ ] Render → *Logs*: request lines show **different `ip=` values per visitor** (public addresses, not `10.x`)
- [ ] Atlas → *Browse Collections*: a `flowmetrics` database with `users`, `tasks`, … exists

From a terminal you can also run the bundled smoke test against the live site (it needs the demo data):

```bash
node scripts/smoke.mjs https://<your-service>.onrender.com
```

## Free-tier behavior to expect

- **Sleeps after 15 minutes without traffic**; the next request takes about a minute to wake it. Open the URL a minute before showing it to someone. (An uptime pinger that calls `/healthz` every 10 minutes keeps it awake; one always-on service fits inside the 750 free hours.)
- **Atlas pauses a free cluster after 30 days with no connections.** If the site stops working after a long break, open Atlas and click *Resume*.
- Free Atlas limits: 512 MB storage, 100 operations per second. More than enough for this app.
- The Go server doesn't compress responses. The main JavaScript bundle is about 374 KB raw (112 KB if gzipped), which is fine for a demo.

## Updating and operating

- **Deploy a change:** `git push origin main`. Render rebuilds and swaps the new version in when its health check passes.
- **Start with no demo data:** set `SEED_ON_START` to `false` in *Environment*. Also rebuild with the demo hint hidden: in `Dockerfile` set `ARG VITE_DEMO_HINT=false`.
- **Reset the demo data:** Atlas → *Browse Collections* → drop the `flowmetrics` database, then on Render choose *Manual Deploy → Deploy latest commit* (a restart works too). The seed runs again when it finds no demo users.
- **Rotate the secret:** change `JWT_SECRET`; everyone is signed out.
- **Public demo caution:** the demo password is documented in the README, so anyone can sign in as a demo user and anyone can register. Don't store anything real in it.

## Troubleshooting

Read the failure in Render → *Logs* first. The server prints a clear message for the common ones.

| What you see | Cause | Fix |
| --- | --- | --- |
| Log: `database not ready yet … error parsing uri: lookup _mongodb._tcp.… no such host` | The cluster hostname in `MONGO_URI` is wrong, or the cluster is paused or deleted | Re-copy the URI from Atlas (*Connect → Drivers*). Check the cluster isn't paused |
| Log: `… authentication failed` / `bad auth` | Wrong user or password, or `<db_password>` still in the string, or a symbol in the password isn't URL-encoded | Use a letters-and-digits password; remove the `<>`; confirm the user has *Read and write to any database* |
| Log: `server selection error … i/o timeout` (or `connection refused`) | Atlas doesn't allow Render's address | Atlas → *Network Access* → add `0.0.0.0/0` (wait about a minute for it to apply) |
| Deploy fails or keeps restarting; `/healthz` returns 503 | The app can't reach MongoDB (any cause above). The server retries for up to about 90 seconds, then exits | Fix `MONGO_URI` / network access, then *Manual Deploy → Deploy latest commit* |
| Log: `fatal … JWT_SECRET is required and must be at least 32 characters` | The generated secret was deleted | *Environment* → add `JWT_SECRET` with a 32+ character random value (`openssl rand -hex 32`) |
| Log: `fatal … JWT_SECRET still holds the example placeholder` | A value containing `change-me` was set | Replace it with a real random value |
| Sign-in works, but a page refresh signs you out | The refresh cookie isn't being kept | Use the `https://` URL (not `http://`). Check `COOKIE_SECURE=true`. This breaks if the UI and API are put on two different domains, which is why they are one service |
| Sign-in shows "too many attempts" (HTTP 429) for everyone | The rate limiter sees one shared IP | Check the `ip=` field in the logs. If it is a private `10.x` address, `CLIENT_IP_HEADER` isn't being forwarded: set `AUTH_RATE_LIMIT_PER_MIN` to `0` (off) or a larger number |
| "no open ports detected" / deploy times out | The process crashed before listening (look just above in the logs), or `PORT` was overridden | Fix the error above it; don't set `PORT` yourself |
| Page loads after about a minute, then is fast | A sleeping free instance waking up | Expected on the free plan |
| Demo accounts don't exist | `SEED_ON_START` isn't `true` | Set it to `true`, then redeploy; the seed runs on start when the demo users aren't there yet (logs: `seed: demo data created`) |
| Build fails during `npm ci` or `go build` | A transient network error, or an edited lockfile | Retry with *Manual Deploy → Clear build cache & deploy*; check the build log for the failing line |
